# Diversity-aware reranking: Paper 1 starter notebooks

This project provides a PyTorch-first, reproducible starting point for research into diversity-aware reranking and computation-budget policies.

## Contents

- `notebooks/01_mimics_baselines.ipynb` — loads processed MIMICS-Diversification data, encodes query/document text with `sentence-transformers/all-MiniLM-L6-v2`, compares SERP order, dense relevance ranking and MMR, evaluates diversity/relevance proxies, and benchmarks ranking-only latency.
- `notebooks/02_budget_controller_pilot.ipynb` — trains a small decision-tree controller to choose MMR candidate depth under a calibrated latency budget. It must be run after Notebook 01 in the same project folder.
- `notebooks/03_candidate_pool_scaling.ipynb` — pure algorithmic stress test of incremental MMR versus a full pairwise-similarity-matrix implementation over synthetic vectors. It tests computational scaling, not retrieval effectiveness.
- `rerank_paper/core.py` — reusable dataset, embedding, ranking, metric, timing, feature and supervision helpers.
- `tests/test_core.py` — unit tests for core behavior.
- `artifacts/` — output directory generated by notebooks; no user data is included in the starter ZIP.

## Recommended runtime

Use Google Colab for the first run, then repeat final latency experiments on your local machine to measure the deployment environment. The experiments do not train a large model. The sentence-transformer model is used only to encode queries and short candidate snippets; MMR and the controller are lightweight.

- A 4 GB dedicated GPU is adequate for the compact embedding model with small batches. CPU ranking is the default because MIMICS typically has fewer than ten candidates.
- Do not count 8 GB of shared GPU memory as equivalent to 8 GB of dedicated VRAM. If CUDA memory is tight, lower `batch_size`, set `EMBEDDING_DEVICE = "cpu"`, or use Colab.
- Colab GPU availability is variable. Report the exact GPU/CPU, PyTorch version, thread count and timing boundary in the paper.

## Running in Google Colab

1. Download and extract `reranking_research_starter.zip` into `/content/reranking_research_starter`.
2. Open `notebooks/01_mimics_baselines.ipynb` from that extracted folder.
3. Run all cells. If processed MIMICS files are missing, it will run a clearly labelled synthetic smoke test so the software path can be checked.
4. Run `notebooks/02_budget_controller_pilot.ipynb` in the same extracted project directory and runtime.
5. Run `notebooks/03_candidate_pool_scaling.ipynb` independently.

In a local Jupyter environment, open the notebooks from this project directory after installing the requirements. Install the appropriate PyTorch build for your OS/CUDA combination using the official [PyTorch installation selector](https://pytorch.org/get-started/locally/).

## Preparing real MIMICS data

The baseline loader expects these processed files in either `MIMICS-Diversification/data/` or `data/` under the project root:

- `serps.pkl`
- `id2doc.pkl`
- `query2qid.json`
- `judgement.tsv`
- `train_qids.npy`
- `test_qids.npy`

Upstream instructions: [DengZhirui/MIMICS-Diversification](https://github.com/DengZhirui/MIMICS-Diversification). That project asks users to obtain MIMICS-ClickExplore and the Bing SERP archive separately, then run `process_mimics.py`. The currently published script has local absolute paths near the top; edit `mimics_path` and `serps_path` to point at your local/downloaded files before running it. Store the outputs in the expected `data/` directory.

The published processing script constructs each document–intent label through keyword matching (`all intent terms are found in document text`). These are weak labels. This notebook is useful for baseline and pipeline development, but a paper should explicitly report this limitation and seek independent validation.

## Development versus final runs

Notebook 01 initially uses `FAST_DEV_RUN = True`, which loads a subset to check the full pipeline quickly. After a successful run and once the real data is prepared, set it to `False` for the full split. Re-run every cell from the top so the cached embeddings and output files correspond to the selected configuration.

Notebook 02 uses only training-query judgments to form budget-action labels. Test judgments are used only for final metric reporting. Do not fit or tune the controller with labels generated from test data.

## Important scientific limitation

MIMICS-Diversification has a maximum candidate pool of ten documents per query (average about nine). It is appropriate for small-pool intent-aware ranking tests but does not support strong claims about scaling to hundreds of candidates. Notebook 03 isolates scaling behavior on synthetic embeddings, which is not a substitute for real retrieval candidates. Before making scalability claims, evaluate on a larger candidate pool with a documented retrieval setup and appropriate relevance/intent judgments, for example a feasible TREC Web Track setup.

## Tests

From the project root:

The tests validate implementation behavior using synthetic data; they do not validate the scientific hypothesis.

## Reproducibility checklist before submission

- Use query-level train/validation/test splits; never split individual query-document judgments independently.
- Tune `lambda`, top-k, the budget and controller settings on training/validation queries only.
- Report alpha-nDCG and ERR-IA (for intent-aware data), relevance quality, pairwise cosine as a proxy only, p50/p95 (and p99 when sample size supports it), throughput, memory, and embedding cost.
- Separate ranking-only latency from end-to-end query embedding/retrieval latency.
- Benchmark methods on the same candidates, machine, device and measurement boundary.
- Run paired query-level confidence intervals/tests and provide ablations/failure cases.
- Do not report synthetic smoke-test or synthetic scaling numbers as empirical search-performance results.
